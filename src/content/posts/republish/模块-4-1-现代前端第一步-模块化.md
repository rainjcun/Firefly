id="灾难二全局污染所有人都挤在同一间屋子里">灾难二：全局污染——所有人都挤在同一间屋子里</h3><p>回忆一下：<code>cards.js</code> 之所以能跑，是<strong>靠</strong> <code>anime.animate</code>、<code>anime.stagger</code> 这些名字。这就是传统 <code>&lt;script&gt;</code> 的"约定"——<strong>库往当前页面全局提供自己的名字，使用者从全局拿</strong>。</p><blockquote><p>这就好像一个屋子里面，就俩人，其中一个人张三从家里带来了四样东西：笔、墨、纸、砚，放在了一个共享的台面上，然后说屋子里的人随便用。那李四要用笔的时候直接用了。</p><p>但是，如果屋子里的人逐渐变多呢？每个人都会从家里带一些东西放在这个台面上呢？</p></blockquote><p>等项目长得更大，你引的库就不只 anime.js 了——再加一个图表库、一个日期处理库、一个 ajax 工具库……<strong>每个库</strong>都靠"往页面上挂自己的名字"的方式提供功能。</p><p>那么——<strong>万一两个库都挂了同名的东西，会怎么样？</strong></p><p>你大概能猜到答案：<strong>会撞名</strong>。而 JavaScript 全局空间里，一个名字只能存一个值——<strong>后来挂上去的，会悄悄盖掉先挂上去的</strong>，没人通知你。</p><p>这种现象，在编程领域有一个专门的词，叫 <strong>全局污染</strong>（global pollution）。</p><p>打个现实里的比方：</p><blockquote><p>张三放在屋子里的纸是用来写字的，后来又来了一个赵六带来了一包纸巾，也叫"纸"，因为赵六来得晚一点，所以在台面上，他的"纸"就覆盖了张三的纸。</p><p>这带来的后果就是，李四某次需要用纸写字的时候，发现根本就写不成。</p></blockquote><p>代码世界里的全局污染就是这种感觉：你拿到的"纸"，可能不是你以为的那一个。等到 <code>cards.js</code> 里那句 <code>anime.animate(...)</code> 跑出诡异结果，你完全猜不到它<strong>到底用的是哪一个 <code>anime</code></strong>——是 CDN 引来的那个？还是被某个后引的库悄悄替换掉的那个？</p><p>项目小的时候，你能记住每个库挂了什么、自己写了什么。<strong>项目一长大，撞名就是迟早的事</strong>——而每一次撞，都是一个让人抓破头的 bug。</p><hr><h2 id="破局方法">破局方法</h2><p><code>&lt;script&gt;</code> 顺序 + 全局污染——它们看着是两件事，根上是同一件事：</p><blockquote><p><strong>“全堆在一起 + 全局名称（变量） + 手排顺序"的传统组织方式，本来就不是给"严肃项目"准备的。</strong></p></blockquote><p>不是工程师的水平不够；是工具本身到了它的能力上限。</p><p>全世界的前端开发者，都撞过这堵一模一样的墙。这堵墙撞多了，他们慢慢长出来一整套翻越它的方法——这套方法，统称叫”<strong>工程化</strong>"。</p><p>它的<strong>第一招</strong>，叫<strong>模块化</strong>。</p><hr><h2 id="模块化的实现方法">模块化的实现方法</h2><p>在看具体代码之前，先用一段话把模块化是什么讲清楚。它和传统方式<strong>只在一件事上不一样</strong>——</p><blockquote><p><strong>传统方式</strong>：你写的东西默认"全世界都看得见"（都堆在一个叫做 <code>window</code> 的全局空间里），库提供的功能也默认"全世界都看得见"。<strong>共享靠"公共"</strong>。</p><p><strong>模块化</strong>：你写的东西默认"只有自己看得见"；想给别人用，得<strong>明文标 <code>export</code></strong>；想用别人的，得<strong>明文写 <code>import</code></strong>。<strong>共享靠"明文声明"</strong>。</p></blockquote><p><code>export</code> 和 <code>import</code> 就是模块化的两个新词。它们做的事都很简单：</p><ul><li><strong><code>export</code></strong>：在文件里给某个东西打上"对外可用"的标记——<strong>没标的，外面拿不到</strong>。</li><li><strong><code>import</code></strong>：在文件顶部明文写"我要用某个文件里的某个东西"——<strong>不写的，你就用不到</strong>。</li></ul><blockquote><p>你<strong>完全不用学怎么写它们</strong>。我们不教语法。你只要了解这两个词、记住它们各自起什么作用就够了。</p></blockquote><h3 id="顺便交代一个名词什么是-es">顺便交代一个名词：什么是 “ES”</h3><p>后面我们会反复看到 “<strong>ES 模块</strong>"、”<strong>ES6</strong>“这一类说法。我们顺手把这个词解释清楚——</p><blockquote><p><strong><code>ES</code> 是 <code>ECMAScript</code> 的缩写</strong>，它是 <strong>JavaScript 这门语言的"官方标准规范”</strong>。 所有浏览器、所有 JS 引擎，都得按照这份规范来实现 JavaScript。 你也可以这样理解：<strong>我们日常说的"JavaScript"，本质上就是"按 ECMAScript 规范做出来的那套东西"</strong>。</p></blockquote><p>所以：</p><ul><li><strong>“ES 模块”</strong> = “JavaScript 标准里定义的那套模块系统”——它不是另一种语言、也不是什么新东西，<strong>就是 JavaScript 自带的官方模块方案</strong>。</li><li><strong>“ES6”</strong> = ECMAScript 的<strong>第 6 版</strong>（2015 年发布）。我们刚才说的 <code>import</code> / <code>export</code>，就是在 ES6 这一版里<strong>被正式定义</strong>的。</li></ul><blockquote><p>记住一句话就够了：<strong>看到"ES"，就在脑子里替换成"JavaScript 官方标准"</strong>。</p></blockquote><hr><p>听上去像是给自己添麻烦——以前 <code>window</code> 空间里全是大家都能拿的东西，现在每个东西都得明文 export、明文 import。可这恰恰是模块化最有价值的地方——它<strong>直接把前面两痛的根拔了</strong>：</p><ul><li>想知道一个文件依赖什么？翻到顶上看 <code>import</code> 那几行——<strong>白纸黑字写在那儿</strong>。再没有"暗依赖"，script 顺序坑自然不存在。</li><li>两个文件想用同名的东西？<strong>根本撞不上</strong>——每个文件 <code>import</code> 进来的，都只活在自己模块里的局部变量。回到 “纸” 那个比喻：<strong>每个人都有了自己的小柜子</strong>，再也不挤一个共享的台面上。</li></ul><p>下面我们就把项目按照模块化改造一遍，看看 <code>import</code> / <code>export</code> 在真代码里长什么样。</p><hr><h2 id="把我们的项目按照模块化来改造">把我们的项目按照模块化来改造</h2><p>首先，我们重写 id="模块化改造之后的访问方式">模块化改造之后的访问方式</h2><p>改完之后，你大概会迫不及待地刷新浏览器、看看新版本跑不跑——可你很快会撞上一个意外：</p><blockquote><p><strong>页面是白的，F12 控制台一行跟 CORS 有关的错误。</strong></p></blockquote><p>这不是你哪里改错了——而是 ES 模块的一条<strong>新规矩</strong>：</p><blockquote><p><strong>ES 模块文件必须通过"服务器"提供出来才能加载——浏览器不允许直接从 <code>file://</code> 读取。</strong></p></blockquote><p>也就是说，从这一刻起，<strong>双击 <code>index.html</code> 直接打开</strong>这种我们从模块 3 一路用过来的方式，<strong>对模块化的代码不再适用了</strong>。</p><h3 id="为什么这么严格">为什么这么严格？</h3><p>简单说，ES 模块走的是浏览器<strong>加载网络资源</strong>的那一套机制——每个模块文件都得被"正式请求"，有"来源"（origin）才行。而 <code>file://</code> 这种"本地直接打开"，<strong>没有真正意义上的来源</strong>——浏览器干脆不许。</p><blockquote><p>背后是安全考虑：模块化代码可以从一个文件 <code>import</code> 另一个、还能从网络 <code>import</code> 别人的库。如果浏览器对"本地双击打开"也开这道门，意味着任何一个你不小心双击的 html 文件，都能读你硬盘上的别的文件、或者悄悄从网络上拉一堆代码下来跑——<strong>这是个大漏洞</strong>。</p><p>浏览器一刀切：模块化的代码，<strong>得走服务器</strong>。</p></blockquote><h3 id="服务器你早就有了">服务器你早就有了</h3><p>这台"服务器"，你早就有了——<strong>模块 3.5 那台 Nginx 云主机</strong>。把项目部署上去（模块 3.5 教过的那一整套：push → 服务器 pull → Nginx 指向它），打开公网 IP，就能看到改造后的项目跑起来的样子——清爽的代码组织、流畅的卡片入场、丝滑的 scramble 数字。</p><blockquote><p>模块 3.5 教你"把网页发布到服务器"，在这里马上就用上了——一点都没浪费。</p></blockquote><hr><h2 id="js-的模块化演变之路">JS 的模块化演变之路</h2><p>你可能会想：这套"<code>&lt;script&gt;</code> 顺序、全局污染"的痛，世界上的开发者一定撞了好几年才发现的吧？</p><p>不止"几年"——<strong>整整 20 年</strong>。</p><p>JavaScript 这门语言从 <strong>1995 年</strong>诞生，<strong>前 20 年没有官方的模块系统</strong>。所有人都用 <code>&lt;script&gt;</code> 标签拼项目、靠 <code>window</code> 全局变量传东西、手排 script 顺序——你刚才在改造前那一版项目里看到的那堵墙，<strong>整个前端界撞了 20 年</strong>。</p><p>这 20 年里，工程师们当然没坐着干等——他们在自己的领域里摸索出了各种"模块化"方案。其中最有名的一个，是 2009 年随着 Node.js 诞生的 <strong>CommonJS</strong>。它和我们今天用的 ES Modules <strong>本质是同一回事</strong>——同样的思想（每个文件管好自己的依赖、互不污染），只是写法略有不同。但 CommonJS 终究是社区自己的方案，不是 JavaScript 这门语言<strong>自己</strong>的官方标准。</p><p>直到 <strong>2015 年</strong>，JS 在 ES6 这个版本里<strong>正式定义了 <code>import</code> / <code>export</code> 语法</strong>——模块化从这一天起，才真正成为 <strong>JavaScript 语言底层支持的标准</strong>；<strong>2017 年前后</strong>，主流浏览器（Chrome、Safari、Firefox、Edge）才陆续原生支持 <code>&lt;script type="module"&gt;</code>。</p><p>也就是说，你刚才写下的 <code>import { animate } from "..."</code> 这件事，<strong>真正能用还不到十年</strong>。但它一出场，就把前 20 年的痛<strong>一并根治</strong>了。</p><blockquote><p>这就是为什么我们说"模块化是工程化的<strong>第一块基石</strong>"——它不是某个聪明人随手发明的工具，是 <strong>20 年的痛逼出来的</strong>那条路。</p><p>顺带也解释了你刚撞上的那个"不能双击打开"——新东西换来了好处，也带来了一些<strong>比以前严格的规矩</strong>（都是为了安全）。</p></blockquote><hr><h2 id="你刚才其实做了一件大事两件灾难悄悄被治了">你刚才其实做了一件大事——两件灾难，悄悄被治了</h2><p>慢一拍，回头看一眼你刚才改完的代码。前面那两件让人抓狂的灾难，<strong>已经各自被根治</strong>——它们怎么消失的，我们盘一盘。</p><h3 id="第一件script-顺序坑消失了">第一件：script 顺序坑，消失了</h3><p><strong>改之前</strong>，HTML 底部是四行 <code>&lt;script&gt;</code>，顺序错一格就崩。 <strong>改之后</strong>，HTML 底部只剩<strong>一行</strong> <code>&lt;script type="module" src="js/main.js"&gt;</code>。</p><p>那 <code>main.js</code> 又是怎么知道要先加载 anime.js、再跑 <code>cards.js</code> 的？——看 <code>cards.js</code> 顶上那行 <code>import { animate, stagger } from "..."</code>。浏览器读到这句，会<strong>自己</strong>去取那个网址、加载完再回来跑 <code>cards.js</code>。<strong>顺序由代码声明、浏览器执行</strong>——再也不藏在 <code>&lt;script&gt;</code> 的排列里。</p><p>我们刚刚亲手把"暗依赖"变成了"明依赖"。</p><h3 id="第二件全局污染根本不存在了">第二件：全局污染，根本不存在了</h3><p><strong>改之前</strong>，那行 anime.js CDN 的 <code>&lt;script&gt;</code> 把 <code>anime</code> 挂到了 window 全局上，所有文件共用。 <strong>改之后</strong>，你<strong>亲手删掉了那行 CDN <code>&lt;script&gt;</code></strong>——<code>anime</code> 这个名字，在你这个项目里<strong>再也不存在于全局空间</strong>。</p><p><code>cards.js</code> 和 <code>score.js</code> 各自顶上 <code>import</code> 自己要用的部分进自己的文件里。两个文件里都叫 <code>animate</code> 的那个名字，<strong>根本不是同一个东西</strong>——各自只活在自己的文件里。</p><p>回到我们"屋子里那张共享台面"的比方：<strong>模块化等于给屋子里每个人配一个自己的私人小柜子</strong>——张三的笔墨纸砚锁在他自己柜子里、赵六的也锁在他自己柜子里，不再共用台面。要从别人那里"借"东西？<strong>得明文写 <code>import</code> 去借</strong>。</p><blockquote><p>想引第二、第三个库？各自 <code>import</code> 就行，不再挤一个公共空间、不再担心谁覆盖谁。</p></blockquote><hr><h2 id="改造前-vs-改造后摆一起对比">改造前 vs 顺序坑、全局污染——这两件事都是"全堆在一起"自带的毛病，项目越大越疼</li><li>这不是你的错——是这种组织方式自己到头了；翻越它的那套东西，统称”<strong>工程化</strong>"</li><li><strong>第一招：模块化</strong> —— 每个文件用 <code>import</code> / <code>export</code> 自己声明依赖，浏览器替你算顺序，全局不再被污染（<strong>你不用学怎么写 <code>import</code>，只要懂它带来的变化</strong>）</li><li>模块化有个小代价：代码不能再双击打开，<strong>得通过服务器跑</strong>——而模块 3.5 那台 Nginx 你已经有了，原样部署上去就能看</li><li>顺便见识了"生态的力量"——别人打磨好的工具（像
